# Week 6 Observation Report · Frequent Itemsets (A-Priori & PCY)

## Task 1 · A-Priori, and Why the Second Pass Is the Whole Problem

- **신뢰도(Confidence)의 비대칭성과 실제 유용한 규칙 방향**:
  - $\text{conf}(i \to j) = \frac{\text{support}(\{i, j\})}{\text{support}(\{i\})}$는 분모가 선행절(Antecedent) $i$의 지지도로 달라지므로 대칭적이지 않습니다.
  - 예를 들어 20,000개 장바구니 벤치마크 데이터(`support = 50`)에서 빈발 쌍 `{1468, 0}`(동시 등장 `52`회, `support({1468}) = 62`, `support({0}) = 13,080`)의 양방향 신뢰도를 비교하면:
    - **`1468 -> 0`의 신뢰도**: $52 / 62 = \mathbf{0.8387}$ (`83.87%`)
    - **`0 -> 1468`의 신뢰도**: $52 / 13,080 = \mathbf{0.0040}$ (`0.40%`)
  - 조건부 예측("A를 산 사람이 B도 살 확률") 관점에서는 신뢰도가 83.9%인 `1468 -> 0` 방향만이 유의미한 주장처럼 보이지만, 아래 향상도(Lift) 분석에서 보듯 후행절(`0`) 자체의 기저 인기도를 반드시 함께 따져야 합니다.
- **가장 높은 신뢰도를 가진 규칙과 그 향상도(Lift), 그리고 이 규칙을 신뢰할 수 있는지 여부**:
  - 소규모 검증용 `BASKETS` 데이터(`support = 3`)에서 최고 신뢰도 규칙은 **`diaper -> beer`** (및 `bread -> milk`)로 **신뢰도 `0.800` (`4/5`)**이지만, `beer` 자체가 전체 7개 장바구니 중 5개(`71.4%`)에 등장하는 흔한 상품이어서 **향상도(Lift)는 $\frac{0.800}{5/7} = \mathbf{1.120}$**에 불과합니다.
  - 대규모 벤치마크 데이터(`support = 50`)에서도 최고 신뢰도 규칙은 **`1468 -> 0`** (**신뢰도 `0.8387`**)이지만, 아이템 `0`이 Zipf 분포 1위 상품으로서 전체 20,000개 장바구니 중 `13,080`개(`65.4%`)에 기본적으로 들어 있기 때문에 **향상도(Lift)는 $\frac{0.8387}{13080/20000} = \mathbf{1.2824}$**에 그칩니다.
  - **결론 (신뢰 여부)**: 두 규칙 모두 진짜 강한 구매 연관성으로 **신뢰할 수 없습니다**. 신뢰도가 80% 이상으로 높게 나온 이유는 두 상품이 특별히 함께 팔려서가 아니라 후행절(`beer`, 아이템 `0`)이 원래 누구에게나 잘 팔리는 최고 인기 상품이기 때문이며, Lift가 `1`에 가깝다는 사실이 이를 증명합니다(교재 §6.1.3).
- **2,000개 아이템에서 Brute-Force와 A-Priori(Pass 1 이후)가 필요로 하는 쌍 카운터 수 비교**:
  - **Brute-Force (전체 가능 쌍)**: 2,000개 아이템에 대해 사전 필터링 없이 모든 쌍의 카운터를 미리 할당하면 $\binom{2000}{2} = \frac{2000 \times 1999}{2} = \mathbf{1,999,000}$개(실제 장바구니에 최소 1회 이상 등장한 고유 쌍만 세어도 **`893,456`개**)의 쌍 카운터가 필요합니다.
  - **A-Priori (Pass 1 이후, `support = 50` 기준)**: Pass 1을 거치면 2,000개 중 `1,849`개 단일 아이템이 생존하여 이론적 후보 쌍 공간이 $\binom{1849}{2} = \mathbf{1,708,476}$개로 줄어들며, Pass 2에서 실제 동시 등장하여 생성된 피크 카운터 수는 **`820,259`개**(약 8.2% 감소; 만약 `support = 200`이면 생존 아이템 `345`개, 피크 카운터 **`58,626`개**로 93.4% 감소)입니다.

## Task 2 · Lower the Threshold Until Your Machine Says No

- **감당하기 어려워진 지지도(Support) 임계값과 가장 먼저 바닥난 자원**:
  - `support`를 `400 -> 200 -> 100 -> 50 -> 25 -> 12 -> 6 -> 3`으로 낮추었을 때, **`support = 50`에서 `25`로 내려가는 순간 A-Priori의 Pass 1 단일 아이템 가지치기(Pruning) 능력이 완전히 바닥났습니다**.
  - `support = 25`부터는 전체 카탈로그 아이템 `2,000`개가 **100% 전부 생존($|L_1| = 2,000$)**하여 단 하나의 아이템도 Pass 1에서 제거되지 않았고, Pass 2에서 데이터셋 내 모든 고유 쌍(`893,456`개 카운터)을 메모리에 올리면서 Python 추적 메모리(`peak_bytes`)가 `1.1 MB`(`support = 400`)에서 **`102.4 MB`(`support = 50~25`) $\rightarrow$ `156.6 MB`(`support = 3`)로 약 142배 급증**했습니다. 아이템 수가 수만 개 이상인 실무 데이터였다면 이 지점에서 **메인 메모리(RAM)**가 즉각 고갈(OOM)됩니다.
- **지지도 반감(Halving)에 따른 카운터 수의 실제 증가율 (A4)**:
  - 카탈로그가 포화되기 전 구간(`support = 400 -> 200 -> 100 -> 50`)에서 지지도를 절반으로 줄일 때마다 `peak_counters`는 `10,585 -> 58,626 -> 273,701 -> 820,259`로 각각 **`5.54배` $\to$ `4.67배` $\to$ `3.00배`** 증가했습니다.
  - 즉, 단순히 2배씩 선형 증가(Doubling)하는 것보다 **훨씬 심각한 초선형·이차(Quadratic, $\mathcal{O}(|L_1|^2)$) 폭발**을 보였는데, 이는 Zipf 분포의 긴 꼬리(Long tail)로 인해 임계값을 반으로 낮출 때마다 생존 단일 아이템 수 $|L_1|$이 약 `2.36~2.39배`(`146 -> 345 -> 825 -> 1,849`) 늘어나고 후보 쌍 수는 그 제곱인 $(2.38)^2 \approx 5.6$배씩 불어나기 때문입니다.
- **정답(Frequent Pairs) 개수와 카운터 개수의 증가 양상 차이 및 그 의미 (A5)**:
  - `support = 400`에서 `50`까지 낮추는 동안 실제 찾아낸 빈발 쌍(정답)은 `249`개에서 `6,397`개로 **약 `25.7배`** 증가한 반면, 이를 찾기 위해 메모리에 생성한 쌍 카운터는 `10,585`개에서 `820,259`개로 **약 `77.5배`** 폭증했습니다(`support = 50`에서 정답 1개당 128개의 카운터 필요, `99.2%`가 허수 후보).
  - 이는 분석가가 *"조금만 더 희귀한 규칙을 찾고 싶으니 지지도 임계값을 살짝만 낮추자"*고 할 때, 얻게 되는 유용한 규칙의 수는 완만하게 늘어나지만 **중간 후보 카운터 메모리는 제곱으로 폭발하여 시스템이 멈춘다**는 뜻이며, 바로 이 간극(Gap)을 줄이기 위해 Pass 2 이전에 후보 쌍을 걸러내는 **PCY 알고리즘**이 필요합니다.

## Task 3 · Make Pass Two Fit (PCY Algorithm)

- **선택한 해시 버킷 개수(`num_buckets`)와 선택 이유**:
  - 버킷 개수로 **$B = 2^{20} = 1,048,576$개**를 선택했습니다.
  - 20,000개 장바구니(평균 크기 20)에서 매 장바구니마다 발생하는 전체 쌍의 연인원(Total pair occurrences)은 약 $20,000 \times \binom{20}{2} \approx 3,800,000$회입니다. PCY의 비트맵 필터가 높은 정밀도로 작동하려면 **버킷당 평균 해시 누적 카운트($\lambda = \frac{3,800,000}{B}$)가 지지도 임계값(`support = 50`)보다 충분히 작아야** 비빈발 쌍들이 해시 충돌로 인해 우연히 합계 50을 넘기는 거짓 양성(False Positive bucket)을 막을 수 있습니다. $B = 1,048,576$일 때 평균 버킷 부하는 $\lambda \approx 3.62 \ll 50$이 되어, 대부분의 비빈발 버킷이 `0`으로 걸러지고 Pass 2의 피크 카운터 수를 `820,259`개에서 **`12,959`개로 98.4% 절감(`strong`)**할 수 있었습니다.
- **정직한 메모리 회계(Honest Memory Accounting)와 PCY가 실제로 이기기 시작하는 손익분기점 (R5)**:
  - **정직한 메모리 비교**:
    - Pass 1에서 PCY는 `1,048,576`개의 정수 버킷 배열을 유지하고, Pass 2에서는 이를 `1,048,576`비트(**`128 KB`**) 비트맵으로 압축한 뒤 `12,959`개의 쌍 카운터만 유지합니다.
    - 만약 단순히 "정수 슬롯 개수"만 비교하면 Pass 1의 버킷 수(`1,048,576`)가 Baseline Pass 2의 카운터 수(`820,259`)보다 많아 보이지만, **실제 바이트(Byte) 단위 메모리**로 계산하면 이야기가 다릅니다(교재 §6.3.3). Baseline의 해시 테이블 쌍 카운터 1개는 키 `(i, j)`(8B) + 카운트(4B) + 해시 테이블 포인터/버킷 오버헤드로 인해 C에서도 최소 **12~16 Bytes**(Python `Counter`에서는 객체 오버헤드로 인해 `820,259`개가 실측 **`102.4 MB`**, 즉 카운터당 약 **125 Bytes**)를 차지합니다. 반면 PCY Pass 1의 버킷 배열은 키를 저장할 필요 없는 **단순 고정 크기 정수 배열**이므로 C 기준 $1,048,576 \times 4\text{ B} = \mathbf{4.19\text{ MB}}$(Python 리스트 기준 약 `8.4 MB`), Pass 2는 비트맵 `0.13 MB` + 카운터 `12,959`개(Python 기준 약 `1.6 MB`)에 불과하여 **이미 현재 데이터셋에서도 실제 피크 바이트 메모리를 10배 이상 절약**합니다.
    - 또한 버킷 수를 $B = 262,144$($2^{18}$)개로 줄이면 Pass 1의 버킷 슬롯 수(`262,144`)와 Pass 2의 카운터 수(`40,196`, **95.1% 절감**)를 합쳐도 Baseline(`820,259`)보다 슬롯 개수 자체도 3배 이상 적습니다.
  - **PCY가 이기기 시작하는 데이터 규모 손익분기점 (Crossover Point)**:
    - 생존 단일 아이템 수를 $m = |L_1|$, 장바구니 내 총 쌍 발생 횟수를 $T = N \binom{\bar{k}}{2}$, 지지도 임계값을 $s$라 할 때, A-Priori의 Pass 2 카운터 수 $P$는 아이템 카탈로그 크기에 따라 **$\mathcal{O}(m^2)$**으로 폭발하는 반면, PCY가 낮은 오탐률을 유지하기 위해 필요한 버킷 수 $B$는 평균 버킷 부하 조건($\frac{T}{B} \le \frac{s}{5} \implies B \approx \frac{5T}{s}$)에 의해 결정되므로 **카탈로그 아이템 수 $m$과 무관**합니다(게다가 $s$가 전체 장바구니 수 $N$의 일정 비율 $p \cdot N$으로 주어지면 $B \approx \frac{5\binom{\bar{k}}{2}}{p}$로 장바구니 수 $N$과도 무관한 상수가 됩니다!).
    - 따라서 ① **바이트 기준(C 언어 4B 버킷 vs 12B 쌍 카운터)**으로는 후보 쌍 카운터 수 $P > \frac{B}{3}$ (본 실험 설정 $B \approx 10^6$ 기준 $P \gtrsim 350,000$개, 즉 생존 아이템 $m \gtrsim 850$개 또는 `support <= 95`)부터 PCY가 메모리를 이기며, ② **순수 슬롯 개수 기준($P > B$)**으로도 생존 아이템 수가 $m \gtrsim 1,450$개(후보 쌍 $P > 1,048,576$개)를 넘어서는 순간부터 PCY가 압도적으로 승리합니다.
- **버킷 배열 크기를 훨씬 작게 줄였을 때 발생한 현상 (실험 결과)**:
  - 버킷 수 $B$를 $2^{20}$(`1,048,576`)에서 단계적으로 줄이며 `peak_counters`와 절감률을 실측한 결과는 다음과 같습니다:
    - `B = 1,048,576` ($2^{20}$): `peak_counters = 12,959` (**98.42% 절감**)
    - `B = 524,288` ($2^{19}$): `peak_counters = 20,658` (**97.48% 절감**)
    - `B = 262,144` ($2^{18}$): `peak_counters = 40,196` (**95.10% 절감**)
    - `B = 65,536` ($2^{16}$): `peak_counters = 303,272` (**63.03% 절감** — 평균 버킷 부하 $\lambda \approx 58 > 50$이 되면서 해시 충돌로 인해 다수의 비빈발 버킷이 임계값 50을 넘기 시작함)
    - **`B = 16,384` ($2^{14}$), `4,096`, `1,024`**: `peak_counters = 820,259` (**0.00% 절감 — 필터 완전 무력화!**)
  - **원인**: 버킷 수를 `16,384`개 이하로 줄이면 버킷당 평균 카운트가 $\frac{3,800,000}{16,384} \approx 231.9$가 되어 지지도 임계값(`50`)의 4.6배를 초과합니다. 그 결과 비빈발 쌍들의 해시 충돌 합계만으로도 **모든 버킷의 카운트가 50을 넘겨 비트맵의 모든 비트가 `1`이 되며**, Pass 2에서 단 하나의 쌍도 걸러내지 못해 `PlainApriori`와 정확히 똑같은 `820,259`개의 카운터를 생성하게 됩니다(정답 쌍 `6,397`개는 어떤 버킷 크기에서도 손실 없이 동일하게 유지됨).
